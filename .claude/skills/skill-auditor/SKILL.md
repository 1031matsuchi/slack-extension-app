# AIスキル作成・サボり度測定スキル (`skill-auditor`)

どのAIモデル（Claude, Gemini, GPT/Codex等）が実行しても手抜きや解釈ブレが起きない高品質な `SKILL.md` を設計・監査します。

## AIにサボらせない7つの設計手法

スキルを新規作成・改善する際は、単なる散文の説明ではなく、以下の7つの構造を必ず組み込んでください。

1. **判断を機械的なしきい値に変える**: 「適切に」「十分に」などの曖昧語を排除し、「エラー0件」「2ケース以上（正常系・異常系）」のように数値・二値で判定できる基準を書く。
2. **言い訳を先回りで封じる**: AIが省略時に使いがちな言い訳（「軽微な変更なので省略しました」等）を「禁止される言い訳」セクションで明示的に封じる。
3. **散文の指示を「実行ゲート」に変える**: 手順を `Gate 1` → `Gate 2` のように段階化し、前のゲートの完了条件を満たすまで次に進めない制約を設ける。
4. **成果物（Artifact）を強制関数にする**: 作成すべきファイルパスや出力すべき表フォーマットを具体的に指定する。
5. **二重記帳で取りこぼしを検出する**: 「実装ファイル」と「設定ファイル（manifest.json等）」と「テストファイル」の対応表（チェックリスト）で突き合わせを強制する。
6. **順序制約で「最悪の失敗」を防ぐ**: 設計・前提確認 → 実装 → 登録 → テスト作成 → 機械的検証（lint/test）の順序を固定する。
7. **失敗にコストを刻んで注意を向ける**: 手順を飛ばすとどのような致命的障害（例: 相乗りBot全体のクラッシュ）が起きるかを冒頭に明記する。

## スキル品質・サボり耐性 10項目チェックリスト（各10点 / 100点満点）

既存の `SKILL.md` を監査する際は、以下の10項目で採点してください（合格ライン: **80点以上**）：

1. **YAMLフロントマター**: `name`（ケバブケース）と、何を・いつ使うかが明確な `description` があるか？（10点）
2. **曖昧語の排除**: 「なるべく」「必要に応じて」「適切に」などの逃げ道となる表現が排除されているか？（10点）
3. **機械的しきい値**: コマンドのExit Codeや件数など、客観的に合否判定できる数値基準があるか？（10点）
4. **実行ゲート化**: ステップごとにゲートが設けられ、順序制約が明記されているか？（10点）
5. **言い訳封じ**: AIがサボる際によく使う言い訳を先回りして禁止しているか？（10点）
6. **成果物の強制**: 出力すべきファイルパスやレポートのテンプレートが明示されているか？（10点）
7. **二重記帳**: 複数の関連ファイル間の整合性を確認するチェックリストがあるか？（10点）
8. **失敗コストの明示**: ルールを破った際の悪影響・リスクが具体的に書かれているか？（10点）
9. **検証コマンドの明記**: 最後に実行すべき検証コマンド（`npm run lint`, `npm test` 等）が具体的か？（10点）
10. **マルチエージェント同期**: `.agents/skills/<name>/SKILL.md` と `.claude/skills/<name>/SKILL.md` の両方に同一内容が配置され、`AGENTS.md` のスキル一覧表に登録されているか？（10点）

## 新規スキル追加・更新時の必須ゲート

1. `.agents/skills/<skill-name>/SKILL.md` を作成・更新する。
2. ツール間の互換性を保つため、`.claude/skills/<skill-name>/SKILL.md` にも **完全に同一の内容** を書き込む。
3. ルートの `AGENTS.md` の「Available Skills」テーブルにスキル名・用途・パスを追記する。
4. 上記の「10項目チェックリスト」で自己採点を行い、80点未満の場合は改善してから完了とする。
5. `npm run lint` を実行してフォーマットエラーがないことを確認する。
