# 基本設計書

## 1. 目的

本書は、Slack Bot マルチ相乗り基盤の目的、想定利用者、絶対に守るべき中核ルール（不変条件）、非機能要件およびトレードオフ方針を定義します。
詳細実装は [`DETAIL_DESIGN.md`](DETAIL_DESIGN.md)、処理・開発プロセスは [`PROCESS_DESIGN.md`](PROCESS_DESIGN.md)、レイヤ責務は [`LIBRARY_ARCHITECTURE_SPEC.md`](LIBRARY_ARCHITECTURE_SPEC.md) で管理します。

---

## 2. システムの目的

- 複数の Slack Bot を **1つのプロセス・1つの Render 無料インスタンス** で経済的に常時稼働させる。
- 初学者を含む複数メンバーが、`npm run create:app` で雛形を生成するだけで **他メンバーと干渉せず** Bot を追加・開発できる。
- AI 連携（例: メッセージからの予定抽出とカレンダー登録）などの拡張機能を、基盤コードを変更せずに Bot 単位で追加できる。

---

## 3. 中核ルール（不変条件）

以下はどの機能追加・改修でも破ってはならないルールです。違反するPRはマージしません。

| 不変条件 | 内容 |
| :--- | :--- |
| 障害隔離（Fault Isolation） | 1つの Bot のトークン未設定・初期化失敗・リスナー例外が、他の Bot やプロセス全体を停止させないこと |
| 安全なスキップ | トークンが未設定・空文字・`YOUR_*` プレースホルダーの Bot は、例外を投げずに `initApp` が `null` を返してスキップされること |
| 3秒以内の応答 | `commands` / `actions` / `shortcuts` / `views` のリスナーは、処理の最初に `await ack()` を呼ぶこと |
| 二重実行の防止 | 同一 Bot のトークンを複数プロセスで同時に接続しないこと（Socket Mode のイベント分散・二重返信を防ぐ） |
| 秘密情報の非公開 | 実トークン（`xoxb-` / `xapp-`）・APIキー・DB接続情報をコミットしない、ログに出力しないこと |
| テストでの外部通信禁止 | テスト時（`NODE_ENV === 'test'`）は `tokenVerificationEnabled: false` とし、Slack API・外部APIへ実通信しないこと |

---

## 4. 想定利用者（ステークホルダー）

AI エージェントや開発者が設計判断を行う際は、以下の誰にどのような影響があるかを考慮します。

| 利用者 | 主な目的 | 判断時の関心事 |
| :--- | :--- | :--- |
| Slack 利用者（エンドユーザー） | Bot にメッセージ・コマンド・スタンプで依頼し、結果を受け取る | 応答の速さ、誤動作（意図しない投稿・二重返信）がないこと、エラー時に分かる通知 |
| 開発メンバー（初学者を含む） | 担当 Bot の機能を実装・テストする | コードの読みやすさ、説明コメント、手順書どおりに動くこと、他メンバーと干渉しないこと |
| レビュアー | PR の品質・安全性を確認する | 変更範囲の小ささ、完了ゲート（lint / test）の通過、相乗り安全性の担保 |
| チームリーダー | Render へのデプロイ、本番DB（TiDB Cloud）・本番トークンの管理、障害対応 | 起動ログでの切り分けやすさ、環境変数の一覧性、ロールバックの容易さ |
| 外部サービス（Slack API / Gemini API / Google API 等） | — | レート制限・利用料金・認証情報の取り扱い |

## 5. 非機能要件方針

| 観点 | 方針 |
| :--- | :--- |
| **可用性** | ヘルスチェックサーバーは Bot の起動成否に関わらず応答する。外部監視から10分間隔でアクセスし、Render 無料枠のスリープを防ぐ |
| **障害隔離** | `apps/index.js` は Bot ごとに `try...catch`、`app.js` は `Promise.all` 内の各起動処理を `try...catch` で囲み、例外を個別にログ出力する |
| **応答性能** | Slack の3秒ルールを守る。LLM・外部APIなど時間のかかる処理は `ack()` の後、またはイベントリスナー（Bolt が自動 ack）内で実行し、結果はスレッド返信で通知する |
| **セキュリティ** | 秘密情報は環境変数のみで扱う。外部API・DBに渡す前にユーザー入力を検証し、SQLは Prisma のクエリAPIを使う（文字列連結の生SQL禁止） |
| **コスト** | Render Free / TiDB Serverless の無料枠内で運用する。AI 呼び出しは明示的なトリガー（スタンプ・メンション・コマンド）でのみ実行し、全メッセージの常時解析は行わない |
| **保守性・学習容易性** | 初学者が意図を理解できる説明コメントを必須とする。外部npmパッケージは標準ライブラリで代替できない場合のみ追加する |
| **品質ゲート** | `npm run lint`（エラー0件）と `npm test`（失敗0件）を完了条件とする |

## 6. トレードオフ方針

| 競合する要件 | 優先方針 |
| :--- | :--- |
| 機能の便利さ vs 相乗り環境の安全性 | **安全性を最優先**。他 Bot を巻き込む可能性のある設計（グローバル状態の共有、未捕捉例外、プロセス終了処理）は採用しない |
| AI による自動化の範囲 vs 誤動作・コスト | 自動実行よりも**明示的なトリガーと確認**を優先する（例: スタンプ押下時のみ実行、必要に応じて確認ボタンを挟む） |
| 開発速度 vs 品質ゲート | lint / test の省略は認めない。代わりに PR を小さく分割して1回あたりの検証コストを下げる（[`pr-splitting.md`](../guidelines/pr-splitting.md)） |
| 実装の短さ vs 初学者の読みやすさ | 読みやすさを優先する。過度な抽象化・ワンライナーより、説明コメント付きの素直なコードを選ぶ |
| 外部パッケージの便利さ vs 依存の少なさ | `node:test`・`node:http`・`node:fs` 等の標準ライブラリで実現できる場合は追加しない |
