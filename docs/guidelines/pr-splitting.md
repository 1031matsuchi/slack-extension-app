# PR分割ガイドライン

変更規模が大きい Pull Request（PR）は、レビュー精度の低下・コンフリクトの頻発・障害時の切り分け困難を招きます。
特に本リポジトリは複数の Bot が1つのプロセスに同居しているため、1つのPRの不具合が全 Bot に影響する可能性があります。
本ガイドラインでは、変更を安全かつレビューしやすい単位に分割する基準を定めます。

---

## 1. PRの推奨サイズ目安

| 指標 | 推奨ライン | 要分割検討ライン |
| :--- | :--- | :--- |
| **変更ファイル数**（`package-lock.json` 等の自動生成ファイル除く） | 10ファイル以内 | 20ファイル超 |
| **変更行数**（追加＋削除、テスト含む） | 300〜400行以内 | 600行超 |
| **レビュー所要時間** | 15〜30分以内 | 1時間超 |

※ ディレクトリ名変更など機械的な一括変更は行数が多くなっても構いませんが、**機能変更と混ぜず単独のPR**にしてください。

---

## 2. 基本原則：1 PR = 1 関心事

以下の異なる性質の変更を1つのPRに混ぜないでください。

1. **機能追加・バグ修正** と **無関係なコード整形（`npm run lint:fix` の全体適用など）**
2. **基盤コード（`app.js` / `apps/index.js` / `lib/` / `scripts/`）の変更** と **個別 Bot の機能追加**
3. **複数の Bot にまたがる変更**（原則として Bot ごとにPRを分ける）
4. **依存パッケージの追加・更新（`package.json`）** と **アプリケーションコードの大規模変更**
5. **DBスキーマ変更（`prisma/schema.prisma`）** と **大規模なリスナー・サービス改修**
6. **AI エージェント向けルール（`AGENTS.md` / スキル）の変更** と **アプリケーションコードの変更**

---

## 3. 代表的な分割パターン

### パターンA: レイヤ・段階別分割（ボトムアップ）
外部API連携を伴う機能（例: AI による予定抽出とカレンダー登録）に適しています。

1. **PR 1（依存・設定）**: パッケージ追加、`.env.sample` へのプレースホルダー追記、`manifest.json` のスコープ追加
2. **PR 2（サービス層）**: `services/` の実装と、外部APIをモックした単体テスト（リスナー未登録のため Slack 上の挙動は変わらない）
3. **PR 3（リスナー接続）**: リスナー実装・登録と単体テスト、仕様書（SPEC）の更新

### パターンB: リファクタリング先行分割
1. **PR 1（準備リファクタリング）**: 外部から見た挙動を変えずに、リスナーからサービスへの処理抽出やファイル分割のみを行う（既存テストの通過で安全性を証明）
2. **PR 2（本実装）**: 整理された構造の上に新機能や仕様変更を実装する

### パターンC: 縦割りスライス分割（機能単位）
1つの Bot に複数の機能を追加する場合に適しています。

1. **PR 1**: スラッシュコマンドの追加
2. **PR 2**: ボタン操作（actions）・モーダル（views）の追加
3. **PR 3**: App Home 表示の拡張

---

## 4. 分割PRを出す際の注意点

- **各PR単体で完了ゲートを通過すること**: 途中段階のPRでも `npm run lint`（エラー0件）と `npm test`（失敗0件）を満たす。
- **途中段階で他 Bot・本番を壊さないこと**: 未完成の機能はリスナーを登録しない、または環境変数が未設定なら無効になる状態でマージする。
- **関係を明記する**: PR本文に全体像（例: `全3分割の 2/3`）と依存関係（ベースブランチ）を記載する。
- **PR本文に記載すること**: 変更概要、対象 Bot、追加した環境変数、`manifest.json` 変更の有無（Slack 側でアプリ設定の更新が必要か）、テスト結果。
